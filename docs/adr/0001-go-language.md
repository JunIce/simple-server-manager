# ADR-001: 选择 Go 而非 Java/Rust

## 状态
已接受

## 背景
需要实现一个常驻后台的系统级服务管理程序，负责管理数百个异构服务进程。候选语言为 Java、Go、Rust。

## 决策
采用 **Go** 作为实现语言。

## 备选方案

| 方案 | 优点 | 缺点 | 为何不选 |
|------|------|------|---------|
| Java | 生态丰富 | 需 JVM，常驻内存 200–500MB，部署重 | 资源占用过高，不符合常驻服务定位 |
| Rust | 性能极致、内存安全 | 学习曲线陡，开发效率低，团队不熟 | 交付速度慢 |
| Go | 单二进制、内存 20–50MB、原生并发、跨平台编译 | 部分系统 API 需 x/sys 辅助 | **选中** |

## 影响
- 正面：部署简单（单文件）、资源友好、goroutine 天然适配多服务守护。
- 负面：需要额外处理 Windows 与 POSIX 的构建标签差异。
- 配套：引入 `golang.org/x/sys` 补全系统调用。

## 风险与缓解
- Windows 服务 API 封装工作量 → 封装在 platform 层并单测。
