# ADR-008: 运行时/JDK 多版本管理

## 状态
已接受

## 背景
同一台 Windows 主机上常安装多个 JDK 版本（如 JDK 8 与 JDK 17），不同服务依赖不同版本。需要统一管理运行时并让服务绑定指定版本启动。

## 决策
引入 **运行时注册表（RuntimeManager）**：
- 独立 `Runtime` 数据模型（ID / kind / version / home / default），与服务配置解耦。
- Java 服务通过 `java.jdk` 引用运行时，`JavaHandler` 解析为 `java.exe` 绝对路径并注入 `JAVA_HOME`。
- 支持手动注册 + 自动发现（JAVA_HOME / 常见目录 / 注册表）。
- 三级解析：默认 / 精确 ID / 版本前缀。

## 备选方案

| 方案 | 优点 | 缺点 | 为何不选 |
|------|------|------|---------|
| 硬编码 java 命令 | 简单 | 无法多版本、依赖 PATH | 无法满足多 JDK 需求 |
| 每服务直接写 java 绝对路径 | 灵活 | 重复、易错、难迁移 | 缺乏统一管理与复用 |
| 运行时注册表 + 引用 | 复用、可发现、可校验 | 需额外模块 | **选中** |

## 影响
- 正面：运行时复用、集中校验、易迁移（修改 home 即可）。
- 负面：新增 `internal/runtime` 模块与运行时 API。
- 配套：`Config.Runtimes` 随 JSON 持久化；`/api/runtimes/*` 接口。

## 风险与缓解
- 运行时路径失效 → 注册时校验可执行文件存在；启动时再校验并返回明确错误码 `3002`。
- 扩展新类型（node/python）→ Resolver/Discoverer 增加分支即可。
